2. System Architecture
The system stays microservice-based, but the request flow, security boundary, and real-time layer are made explicit so you can defend the design in an interview or demo.
High-level request flow
React SPA (role-aware routing) → API Gateway → JWT filter validates token & role → routes to the correct microservice
Each microservice registers itself with Eureka Server; the Gateway resolves service locations dynamically — no hardcoded URLs
Auth Service is the only service that issues tokens; every other service only verifies them (stateless verification, shared public key or shared secret)
Notification Service listens to domain events (appointment booked, bill generated) via a lightweight event flow and pushes WebSocket + email alerts
Config Server (new) centralizes application.yml values for every service so environment changes don't require rebuilds

3. Multi-Role Authentication & Authorization (RBAC + JWT)
This is the feature that turns a CRUD demo into a real system. Five roles share one login screen but see completely different applications afterward.
Roles
ADMIN — full control: manage users, doctors, departments, view system-wide analytics
DOCTOR — manage own appointments, write prescriptions, view assigned patients' records
RECEPTIONIST — register patients, book/manage appointments, front-desk billing
PATIENT — book appointments, view own records/prescriptions/bills, message doctor
PHARMACIST — view incoming e-prescriptions, manage medicine inventory, fulfill orders
Token design
Access token: JWT, short-lived (15 min), carries userId, role, and permissions claim
Refresh token: longer-lived (7 days), stored as httpOnly cookie, rotated on use
Password hashing: BCrypt with strength 12 in Auth Service
Every downstream service validates the token signature locally (no round trip to Auth Service on every call) — this is what makes it scale
Authorization layers (defense in depth)
Gateway layer: rejects requests with missing/expired/malformed tokens before they reach any service
Service layer: Spring Security @PreAuthorize("hasRole('DOCTOR')") on controller methods
Data layer: row-level checks, e.g. a doctor can only fetch appointments where doctorId == currentUser.id
Frontend layer: route guards hide UI for roles that shouldn't see it — cosmetic only, never trusted as real security
Common mistake to avoid
Never rely on the frontend hiding a button as your only protection. Always re-check the role/ownership on the backend endpoint — frontend guards are for UX, backend checks are for security.

5. Modern UI/UX Design System (Fresh, Non-Template Look)
To avoid the generic 'admin template' look, define a small design system before writing any screen. Everything below is deliberately not the default Bootstrap blue/Material purple that every tutorial uses.
Direction
Concept: 'Calm Clinical' — a healthcare palette that feels trustworthy and modern rather than sterile-white-and-red
Base neutral: warm off-white background (#F7F8FA), not pure white — reduces eye strain on dashboards
Primary: deep teal (#0F766E) — associated with care/health without being a cliché medical red/blue
Secondary/accent: indigo-blue (#2563EB) for interactive elements, links, primary buttons
Ink/navy (#1B2A4A) for headings — higher contrast and more character than plain black
Status colors: success #16A34A, warning #D97706, danger #DC2626 — used sparingly, only for state
Typography
Headings: 'Sora' or 'Space Grotesk' (geometric, modern, free on Google Fonts) — gives the app a distinct identity
Body: 'Inter' — highly legible at small sizes for dense dashboard data
Scale: 12/14/16/20/24/32/40px, consistent 1.25 type ratio
Layout language
Rounded-but-not-bubbly corners: 10px radius on cards, 8px on buttons/inputs
Soft elevation: subtle shadows (0 1px 3px rgba(16,24,40,0.08)) instead of heavy drop shadows
Sidebar: collapsible, icon+label, active item shown with a left accent bar (not a full color block) — a small detail that reads as 'custom built'
Cards with a colored 4px top border keyed to category (e.g., teal for clinical, indigo for admin, amber for billing)
Generous white space, 8px spacing grid throughout
Components to build once, reuse everywhere
StatCard (animated counter + trend arrow)
Timeline item (for patient history and doctor schedule)
SlotPicker (visual grid of available appointment times)
StatusChip (color-coded pill: pending/confirmed/completed/cancelled)
EmptyState illustration component (custom SVG, not a stock icon) for empty lists
Toast notification system for real-time alerts
Dark mode
Ship a real dark theme (not just inverted colors): background #0F1720, surface #1B2634, text #E5E9EF, primary teal brightened to #14B8A6 for contrast
Recommended stack for this look
Tailwind CSS for utility-first styling + CSS variables for the two themes
shadcn/ui or Radix primitives for accessible unstyled components you can restyle completely
Framer Motion for the small transitions (drawer slide-in, count-up numbers, page transitions)
Recharts for the analytics charts
lucide-react for a consistent icon set
Fresh-look rule of thumb
If a component looks exactly like the default styling of the library you imported, restyle it. The goal is that no reviewer can guess which UI kit you started from.

Cross-service references
Since each service owns its own DB, an appointment only stores patientId and doctorId as plain IDs — never a foreign key across databases. Any service needing patient/doctor details calls the owning service's API (or caches a lightweight copy) instead of joining across databases.
9. Real-Time Layer (WebSocket / Notifications / Chat)
Spring's STOMP-over-WebSocket support pairs cleanly with a React client using @stomp/stompjs or sockjs-client.
Notification Service exposes /ws endpoint; each authenticated user subscribes to /topic/user/{userId}
Domain events (appointment confirmed, prescription ready, bill generated) are published internally and forwarded as WebSocket messages plus optional email/SMS
Frontend shows a bell icon with unread count and a toast for the current session
Optional: simple doctor↔patient chat scoped to an active appointment, using the same WebSocket channel
Keep it simple first
You do not need Kafka/RabbitMQ for a student/portfolio project — a direct service call or a lightweight in-process event publisher into the Notification Service is enough, and easy to upgrade to a real message broker later if you want that on your resume too.
10. Phase-by-Phase Development Roadmap
Build in this order. Each phase produces something runnable/demoable — don't move on until the current phase works end to end.
Phase 0 — Environment & Repo Setup
Install JDK 21, Maven, Node.js LTS, MySQL, Git, IntelliJ/VS Code, Postman, Docker Desktop
Create a mono-repo or multi-repo GitHub structure: /backend/<service-name>, /frontend
Set up a shared 'common' Maven module for DTOs/exceptions used across services (optional but clean)
Phase 1 — Platform Skeleton
Build Config Server, then Eureka Server, confirm both run standalone
Build API Gateway with basic routing to a placeholder service; confirm Eureka registration works
Phase 2 — Identity & Access
Build Auth Service: register/login, password hashing, JWT issue + refresh
Add role field and seed 5 role types; write the JWT filter shared logic (as a library or copied config) for downstream services
Wire the Gateway to reject invalid tokens before forwarding
Build the React login/register screens and route guards; confirm role-based redirect after login
Phase 3 — Core Domain Services
Patient Service: CRUD + medical history + vitals endpoints
Doctor Service: CRUD + availability slot management
Appointment Service: slot-aware booking, conflict checks, status transitions
Connect each to its own MySQL schema; verify with Postman collections per service
Phase 4 — Dashboards & UI System
Build the design system first: colors, typography, base components (Button, Card, Input, StatusChip, StatCard)
Build Admin dashboard, then Doctor, then Receptionist, then Patient, then Pharmacist — reuse the same component library
Wire each dashboard to its real endpoints; replace all mock data before moving to Phase 5
Phase 5 — Billing, Pharmacy & Notifications
Billing Service: invoice generation on appointment completion, payment recording
Pharmacy Service: prescription intake, inventory decrement on dispense
Notification Service: WebSocket channel + email templates; hook into appointment/billing/prescription events
Phase 6 — Advanced/New Features
Analytics charts on Admin dashboard (Recharts)
Global search bar
Optional: telemedicine video room, AI symptom pre-check, payment gateway sandbox integration
Phase 7 — Testing, Hardening, Deployment
JUnit + Mockito for each service's service/controller layer
Run SonarQube, fix flagged issues, aim for 80%+ coverage on business logic
Dockerize every service + docker-compose for local multi-service run
Deploy (Render/Railway/EC2 for backend, Vercel/Netlify for frontend) and record a demo video

13. Code Quality, Security & Observability
Code quality
SonarQube target: 0 bugs, 0 vulnerabilities, coverage >80% on service/controller layers, maintainability rating A
Consistent DTO layer — never expose JPA entities directly in API responses
Security
BCrypt for passwords, HTTPS in deployment, CORS locked to the known frontend origin
Rate limiting on the Gateway for /auth/login to slow brute-force attempts
Input validation (Bean Validation annotations) on every DTO
Audit log table capturing user_id, action, entity, timestamp for sensitive actions (role changes, prescription edits)
Observability
Spring Boot Actuator health endpoints on every service, surfaced on the Admin dashboard's system-health widget
Centralized logging (even simple file-based initially; ELK stack as a stretch goal)

17. Connecting MySQL & Full Database Schema
This section makes the database layer concrete: exact schema for every service database, and the Spring Boot configuration to connect each microservice to its own MySQL schema. Ready-to-run .sql files for every schema below are included alongside this document — run them once and every service has real tables to read/write from day one.
17.1 Install & prepare MySQL
Install MySQL Server 8.x and MySQL Workbench (or use the MySQL CLI).
Start the MySQL service and log in as root: mysql -u root -p
Create one schema per microservice (database-per-service pattern) — the .sql files provided do this for you.
Run the combined script, or each file individually:
mysql -u root -p < sql/01_auth_db.sql
mysql -u root -p < sql/02_patient_db.sql
mysql -u root -p < sql/03_doctor_db.sql
mysql -u root -p < sql/04_appointment_db.sql
mysql -u root -p < sql/05_billing_db.sql
mysql -u root -p < sql/06_pharmacy_db.sql
mysql -u root -p < sql/07_notification_db.sql
17.2 Add the MySQL driver to each Spring Boot service
In every service's pom.xml:
<dependency>
  <groupId>com.mysql</groupId>
  <artifactId>mysql-connector-j</artifactId>
  <scope>runtime</scope>
</dependency>
17.3 application.yml per service
Each microservice points at its own schema only — this is what keeps services independently deployable. Example for Patient Service (application.yml):
server:
  port: 8082
 
spring:
  application:
    name: patient-service
  datasource:
    url: jdbc:mysql://localhost:3306/patient_db?useSSL=false&serverTimezone=UTC&createDatabaseIfNotExist=true
    username: root
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver
  jpa:
    hibernate:
      ddl-auto: validate
    show-sql: true
    properties:
      hibernate:
        format_sql: true
        dialect: org.hibernate.dialect.MySQL8Dialect
 
eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka/
ddl-auto: validate, not update
Since you already have hand-written schema files, set ddl-auto to validate (Hibernate checks your @Entity classes match the real tables but never silently alters them) or none. Reserve update/create for quick local experiments only — never in a shared or graded build.

17.4 Entity to table mapping example
One worked example so the pattern is unambiguous — Patient entity mapped to the patients table already created by the schema script:
@Entity
@Table(name = "patients")
public class Patient {
 
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
 
    @Column(name = "user_id", nullable = false)
    private Long userId;
 
    @Column(name = "first_name", nullable = false, length = 80)
    private String firstName;
 
    @Column(name = "last_name", nullable = false, length = 80)
    private String lastName;
 
    private LocalDate dob;
 
    @Enumerated(EnumType.STRING)
    private Gender gender;
 
    @Column(name = "blood_group", length = 5)
    private String bloodGroup;
 
    private String phone;
    private String address;
 
    @Column(name = "emergency_contact")
    private String emergencyContact;
}
